確定済み詳細ログによる負荷トップ10

更新日: 2026-10-14 UTC。これはVF2のWasm移植で保存した最新の確定済み詳細分類を再掲したもので、現在のライブ負荷ではない。以後の通常速度の測定は別に存在するが、同じ細かさの分類ではない。SegaRetro原文・翻訳とも別の独立解析である。

機種・場面・計測方法

Apple M3 Ultra、Darwin 25.3.0、Chromium 147.0.7727.15、390×844のデスクトップ画面、実際のWorker数1。音声CPUはON、ライブAudioWorklet再生はOFF、通常フレームペーシングはOFF。戦闘の元フレーム2000–2599、3回。

計測期間は2026-10-14 16:54:38.854–16:56:25.654 UTC。ビルド・ハーネスcommitはともに 4bce5ff28f3aaba321cd13b2d49383f1da2c4d14。CPUとschedulerの関数境界を保持する診断ビルドで、通常ビルドとコンパイラの最適化条件が異なる。スマートフォン実機、最新UIのリアルタイム値、通常のWebKitの内訳ではない。

各サンプルのcall stackをleafからrootへ見て、最初に認識した分類へ一度だけ割り当てる。分母は同じWorkerプロファイルの全sampleのtimeDelta合計で、idle・JS・GC・未分類も含む。主スレッド、Canvas、compositor、AudioWorkletや物理表示はこのWorker内訳の対象外。

換算ms/frame = 分類のtimeDelta合計[µs] / 1000 / 600。各行は3試行の中央値（最小–最大）。直接のストップウォッチ計時ではない。各行の中央値は独立に求めるので、足して正確に100%や全時間になるとは限らない。

サンプル数は3,709 / 3,711 / 3,692、分母の時間は5,565,663 / 5,570,465 / 5,547,681µs。要求周期は1,000µsだが記録された平均timeDeltaは約1,500–1,503µs。未サンプル末尾880 / 1,167 / 1,285µsは分母に含めない。サンプリングONの追加workコストは同じ境界保持ビルドに対して中央値+0.9263%（+0.5745–+1.5272%）だった。診断ビルド自体の通常ビルドとの差をこの数字で消せるわけではない。

次に調べる範囲

最大分類はソフトウェア3D、次がscheduler/UART。TGPは3位だが、命令デコード・ALU・バス・FIFO待機を個別の費用へ分離できていない。見える関数のselfサンプルではTGP execute_run が全sampleの約6.4276%、alu_pre が約1.2622%。これをTGP分類9.3787%へ追加すると重複するので足さない。また execute_run のselfはデコードだけの時間ではない。

TGPの汎用事前デコード、残存するバス間接呼び出しの特殊化、FIFO構造の改善は候補であり、改善率は未測定。静的再コンパイルにはアップロード変更の検出、stall、slice終了、浮動小数の順序、サイクル予算と参照実行への切り戻しが必要。既存のi960 AOTがあることをTGPもAOT化済みという意味にしない。

VF2エミュレータの独立解析 — TGP・入力判定・資料の検証

更新日: 2026-10-14 UTC。対象はVF2 Version 2.1向けModel 2AエミュレータのWasm移植。これはプロジェクトで実施した独立解析であり、SegaRetro記事の原文・翻訳とは別の文書である。実コード、既存の検証記録、メーカー資料を区別し、未確認事項を明示する。スマートフォン実機での性能・熱・電力は今回測定していない。

TGPは最適化できるか

改善の候補はある。ただし現時点でTGPを高速化したという実測結果はない。 既存診断では戦闘時のWorkerサンプル時間の約9.38%がTGP分類だった。命令デコードの頻度、バス呼び出しの実コスト、FIFO待機の割合をさらに分けてから、限定した変更を一つずつ試す段階である。

現在の実装経路

  • メインi960: ビルド時に生成するコードによる実行と、必要時のインタプリタへの切り戻し。
  • TGP: MB86234用にアップロードされたプログラムを、mb86233_device が解釈実行。
  • 描画側geometry: Model 2/2A用のHLE。TGP命令を実行する経路とは別。
  • Z-sort・クリップ・ポリゴン描画: ホスト側のソフトウェア実装。その後に2D合成・色変換・画面送信が続く。

mb86233というクラス名だけでModel 1の実装と判断したり、i960にAOTがあることをTGPのAOT化済みと読み替えたりしない。ハードウェア図のブロック数はホストWorker数を意味しない。

解析したソース基準commitは 88af23fa8fb90963c81605bf9cb1ebc77df00310。対応箇所はリポジトリ内の src/machine/model2a.cpp の tgp_bus / copro_fifo_w / timeslice、src/core/mb86233.cpp の execute_run、src/machine/model2_video.cpp の geo_parse / frame_end。これらはソース内の位置を示す識別名で、公開GitリポジトリのURLではない。

前者のビルドcommitは d0932173cfc035bfee7f1e83e81e8f1987e3263c、ハーネスは b653084c6c3891ce2ed63207ccf18899c447f457。後者はビルド・ハーネスとも 4bce5ff28f3aaba321cd13b2d49383f1da2c4d14。

割合は「TGPに分類したサンプルのtimeDelta合計 ÷ 同じWorkerプロファイルの全timeDelta合計」。分母はidle・JS・GC・未分類も含む。leafからrootへ最初に一致する分類へ一度だけ配分するので、TGP内から別分類の関数を呼ぶ時間はその分類に入る場合がある。TGP機能全体の厳密な包括時間ではない。

3.64%から9.38%への違いは、TGPの実負荷増加を示さない。 関数境界の保持はコンパイラのインライン化を変え、帰属先を見やすくする一方で実行コードも変える。境界保持版ではサンプリングをONにする追加コスト自体も中央値約0.9263%あった。通常ビルドの直接計時、OSのCPU利用率、今回のWebKitでの68000計時、スマホの性能とは条件が異なる。9.38%からFPS向上率を予測しない。

同じ境界保持診断でTGP execute_run のself分類は約6.4276%、alu_pre は約1.2622%。ただしインタプリタ内部で命令種類別にどこが支配的かはまだ分からない。より大きい分類にはソフトウェア3D約34.16%、scheduler約22.61%もあり、TGPだけを最適化すれば全体の問題が解決するとは言えない。

現在のTGPカウンタ m_tgp_instructions は、名前に反して run() の消費サイクルを加算する。ALU演算の追加サイクルやstall再試行があるため、完了命令数やホスト時間として扱わない。

初回のコード変更は、必要な頻度を得た後の事前デコード単独実験が範囲を限定しやすい。改善幅は未測定であり約束できない。浮動小数の結合順・旧値と新値の反映順、lookup table、FIFOの空／満、CPU停止と再開を保つ。fast-math、FMA化、host三角関数への置換、UARTイベント削除、ゲストサイクル削減はこの候補に含めない。

採用には、現行インタプリタを基準にした合成命令・数値・メモリ境界の差分試験、TGP内部状態と副作用の比較、全フレームの画像・PCM、順序付きイベント監査、入力・音声などの統合ゲートが必要。その後に同一ソースの対照／候補を、実際の3スレッド／1Worker、ライブ音声付き通常速度で比較する。カウンタ診断の時間を通常FPSの改善値として流用しない。

技入力・成立・当たり・ガードの解析

独歩頂膝と崩撃雲身双虎掌は、入力からゲーム内のアクション成立と体力減少まで対応する証拠がある。当たり判定の形状・接触計算、通常ガードの詳細条件は未特定。 ゲームの判定処理をJavaScriptで置き換えた実装ではない。

入力はキーボード／タッチ／GamepadからWorkerを通って、active-lowの基板入力ポートへ渡される。その後にゲストi960側の入力履歴・コマンド解釈・アクション・反応処理が動く。ホスト側のキュー受付、入力列の発行完了、技の成立、命中は別の事象である。

まだ分かっていないこと

  • 攻撃・食らい判定が球、カプセル、箱などのどの形で、どの座標・ボーンに結び付くか。
  • 発生・持続・硬直と、判定を有効にするデータ構造。
  • 高さ、距離、向き、投げ範囲、相打ち、無敵、ダウンなどの分岐と補正。
  • それらをi960とTGPがどう分担しているか。
  • 通常ガード成立を示す専用状態、上中下段の分類、受付時機と被弾硬直の関係。

HPの減少を抽出した「hit」は、衝突ルーチンの専用イベントを観測したものではない。描画ポリゴンの重なりからhitboxを推定して確定図として公開する根拠もない。

千本パンチの選定試行では、相手にGを保持させても反復ダメージが継続した。ただし各フレームでガードが成立していた証拠ではなく、「Gが常に無効」「全技がガード不能」という結論にはならない。攻撃側のガードキャンセル遷移を、防御側の通常ガード成功マーカーとして流用しない。

次の検証候補は、同じ再生条件で相手入力だけを無入力／G／下+Gに変え、十分なニュートラル待ちと直前の硬直を分けて比較すること。状態変化のフレームを絞ってから書き込み元・条件分岐へ追跡する。この追加解析は未実行で、命令トレースを性能測定と同時に走らせない。

有力な単位誤記の推定

  • HSyncの「24 Hz」: 数百の走査線と約60Hzの垂直周波数には整合せず、kの脱落が有力。このエミュレータは25MHz/1025=約24.390kHz、さらに424ラインで約57.52416Hzとなる。ただし物理基板の新たな実測ではない。記事の19.523MHzと656×496という別の数値組は約60.00135Hzであり、異なる組の数値を混ぜない。
  • Model 2Bの「80 MAC/sec、1個40」: Analog Devices ADSP-2106xデータシート Rev.H、2013年3月、pp.1–4は40MHz、25ns FIR tapなどを示す。1対/25nsなら1個で毎秒4000万対、2個の理論合計で8000万対となり、millionの脱落が有力。持続するゲーム性能や浮動小数FMAの意味は保証しない。これはModel 2Bの話で、VF2のModel 2AをSHARC実装と読み替えない。

内訳の算術と未解決の差

記事のRAM小計自体は整合する。Original Model 2/2Aは9,776KiB=9.546875MiB、2Bは18,388KiB=17.95703125MiB。しかしOriginalと2Bの見出し総量・ブロック内訳・RAM+最大ROMは同じ範囲として足すと一致しない。2Aの約142MiBは丸めを含めおおむね整合する。

この計算は記事の1,024換算に合わせたもの。最大搭載ROM容量、実ゲームの搭載量、RAM、キャッシュ、共有領域、ホスト上の展開コピーは別に数える必要がある。内訳差の原因や、実基板のチップ容量を確定したわけではない。

記事の68000「12MHz」に対し、この実装と下記MAME比較版は45.1584MHz/4=11.2896MHz、SCSPは/2=22.5792MHz。数値差は確認できるが、丸め、基板差、記載ミスのどれかは未解決。記事の値だけを根拠にエミュレータのクロックを変更していない。
