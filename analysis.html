機種・場面・計測方法

Apple M3 Ultra、Darwin 25.3.0、Chromium 147.0.7727.15、390×844のデスクトップ画面、実際のWorker数1。音声CPUはON、ライブAudioWorklet再生はOFF、通常フレームペーシングはOFF。戦闘の元フレーム2000–2599、3回。

計測期間は2026-10-14 16:54:38.854–16:56:25.654 UTC。ビルド・ハーネスcommitはともに 4bce5ff28f3aaba321cd13b2d49383f1da2c4d14。CPUとschedulerの関数境界を保持する診断ビルドで、通常ビルドとコンパイラの最適化条件が異なる。スマートフォン実機、最新UIのリアルタイム値、通常のWebKitの内訳ではない。

各サンプルのcall stackをleafからrootへ見て、最初に認識した分類へ一度だけ割り当てる。分母は同じWorkerプロファイルの全sampleのtimeDelta合計で、idle・JS・GC・未分類も含む。主スレッド、Canvas、compositor、AudioWorkletや物理表示はこのWorker内訳の対象外。

換算ms/frame = 分類のtimeDelta合計[µs] / 1000 / 600。各行は3試行の中央値（最小–最大）。直接のストップウォッチ計時ではない。各行の中央値は独立に求めるので、足して正確に100%や全時間になるとは限らない。

次に調べる範囲

最大分類はソフトウェア3D、次がscheduler/UART。TGPは3位だが、命令デコード・ALU・バス・FIFO待機を個別の費用へ分離できていない。見える関数のselfサンプルではTGP execute_run が全sampleの約6.4276%、alu_pre が約1.2622%。これをTGP分類9.3787%へ追加すると重複するので足さない。また execute_run のselfはデコードだけの時間ではない。

TGPの汎用事前デコード、残存するバス間接呼び出しの特殊化、FIFO構造の改善は候補であり、改善率は未測定。静的再コンパイルにはアップロード変更の検出、stall、slice終了、浮動小数の順序、サイクル予算と参照実行への切り戻しが必要。既存のi960 AOTがあることをTGPもAOT化済みという意味にしない。

TGPは最適化できるか

改善の候補はある。ただし現時点でTGPを高速化したという実測結果はない。 既存診断では戦闘時のWorkerサンプル時間の約9.38%がTGP分類だった。命令デコードの頻度、バス呼び出しの実コスト、FIFO待機の割合をさらに分けてから、限定した変更を一つずつ試す段階である。

現在の実装経路

  • メインi960: ビルド時に生成するコードによる実行と、必要時のインタプリタへの切り戻し。
  • TGP: MB86234用にアップロードされたプログラムを、mb86233_device が解釈実行。
  • 描画側geometry: Model 2/2A用のHLE。TGP命令を実行する経路とは別。
  • Z-sort・クリップ・ポリゴン描画: ホスト側のソフトウェア実装。その後に2D合成・色変換・画面送信が続く。

mb86233というクラス名だけでModel 1の実装と判断したり、i960にAOTがあることをTGPのAOT化済みと読み替えたりしない。ハードウェア図のブロック数はホストWorker数を意味しない。

解析したソース基準commitは 88af23fa8fb90963c81605bf9cb1ebc77df00310。対応箇所はリポジトリ内の src/machine/model2a.cpp の tgp_bus / copro_fifo_w / timeslice、src/core/mb86233.cpp の execute_run、src/machine/model2_video.cpp の geo_parse / frame_end。これらはソース内の位置を示す識別名で、公開GitリポジトリのURLではない。

技入力・成立・当たり・ガードの解析

独歩頂膝と崩撃雲身双虎掌は、入力からゲーム内のアクション成立と体力減少まで対応する証拠がある。当たり判定の形状・接触計算、通常ガードの詳細条件は未特定。 ゲームの判定処理をJavaScriptで置き換えた実装ではない。

入力はキーボード／タッチ／GamepadからWorkerを通って、active-lowの基板入力ポートへ渡される。その後にゲストi960側の入力履歴・コマンド解釈・アクション・反応処理が動く。ホスト側のキュー受付、入力列の発行完了、技の成立、命中は別の事象である。

回帰検証

  • native ASan/UBSanと最適化Wasmで、それぞれ608,032差分ケースを通過。全mask、反転、透明/opaque、座標出力、8/128ピクセル境界、clip/scroll/split、ランダム矩形、実際のdecode/update/draw経路を比較した。
  • 8回の2,600フレームreplayで20,800組の画像/PCM SHA-256比較と208選択状態チェックが一致。対照を含む比較件数であり、すべてが別々の候補フレームという意味ではない。
  • 4回の専用イベント監査で、各49,296,627イベントの順序付き記録が一致。追加の104画像/PCM/選択状態チェックも一致した。
  • 入力、macro、camera、audio、loader、通常/互換経路、touch配置、motion viewerを含む24機能ジョブが通過した。
  • 性能40runの最終framebufferと選択状態が一致し、live audioのunderrun・overrun・errorは全40runで0。これは上の全frame SHA-256比較とは別の終点検証である。

初回Wasm単体試験では大きなfixtureをstackへ置いたためoverflowし、fixtureだけを静的配置へ変更して再試験を通した。失敗記録を保持し、生産コードで隠す修正はしていない。これらは検証したtraceと選択状態の証拠であり、全場面の完全状態同値性の証明ではない。

不利な結果と未確認事項

確認cohortの1Worker・第5ペアでは、総workが0.125ms、1.3453%増加した。coreは0.02167ms、renderは0.16000ms減少する一方、boardは0.13667ms、RPC残余は0.14000ms、Canvasは0.01500ms増加した。このrunも集計に残している。重なるphaseや別々に取った中央値を加算して全体時間を作らない。

board phaseのペア削減率中央値は4群すべて負で、表の順に−0.4045%、−0.2187%、−1.8302%、−0.5007%。mask単体の利益やboard悪化の原因を、コード配置・host変動・粗い時計から独立に分離できていない。

確認cohortでは両経路の全ペアでRPC残余が悪化したが、coreは全ペアで改善した。RPCは往復時間からWorker時間を引いた量で、メッセージ処理・スケジューリング・未計装処理を含み、純粋な通信遅延ではない。

以前の同じengineの時計確認は隔離経路約0.020ms、非隔離経路約1msだった。今回の性能runに新しいclock probeは挿入しておらず、特に1Workerの細かいphase帰属には制限がある。host負荷は変動し、監視用の読取り接続が中断したことによる測定への影響も定量されていない。測定自体の再起動・run除外はない。

他stage・他character、スマホ実機の持続動作、実touch/controller、発熱・消費電力・全体memory、物理scanoutは未測定。反復した小さいwork改善と一貫したrender/core低減を根拠に、検証済み実装を明示的ローカル利用へ限定する。既定OFFを維持し、全run無回帰や一般向け配備を約束しない。
